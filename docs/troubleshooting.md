# Дерево поиска неисправностей

Накопительный документ. Диагностика (`reality-check diag`) идёт по этим же слоям сверху вниз и на каждом сравнивает взгляд снаружи со взглядом изнутри — виноват тот слой, где эти два взгляда расходятся.

Взгляд изнутри берётся из API панели (состояние Xray, применённый конфиг, логи) и, если есть доступ, дополняется SSH (журнал systemd, фаервол, список слушающих портов). Без SSH диагностика работает — обе разобранные поломки нашлись бы и по одному API.

## L0 — панель недоступна или не пускает

| Признак | Причина | Проверка |
|---|---|---|
| TCP к порту панели не проходит | панель не запущена, сменился порт, режет фаервол | `systemctl is-active x-ui`, `ss -tlnp` |
| приходит HTML вместо JSON | не указан `base_path` (webBasePath) | открыть панель в браузере, посмотреть URL |
| `success:false` на логине | сменился пароль, включилась 2FA | зайти руками; при 2FA заполнить `two_factor_code` |
| Bearer-токен не принят | версия панели старше токенов, токен отозван | `probe` покажет `auth_mode: cookie` |

## L1 — панель отвечает, но конфиг логически мёртв

Инбаунд выключен; клиент отключён; истёк `expiryTime`; выбран лимит `totalGB`; клиента вообще нет в инбаунде.
Косвенный признак «до сервера ни разу не дошли»: нулевой трафик у клиента и пустой `clientIps`.

## L2 — Xray на сервере не работает

Ключевое: в 3x-ui **Xray не отдельный systemd-юнит**, а дочерний процесс службы `x-ui`. `systemctl status xray` там ничего не покажет.

| Признак | Причина |
|---|---|
| `x-ui` не active | служба упала или не включена |
| процесс xray отсутствует / поднят секунды назад | Xray падает в цикле — почти всегда битый конфиг |
| `config.json` не парсится | панель записала невалидный JSON |
| порт есть в панели, но нет в `config.json` | либо Xray не перезапустился после правки, либо инбаунд поднят на узле — у него есть `nodeId`, и в конфиге панели его быть не должно |
| Xray не стартует вовсе | один некорректный инбаунд отвергает весь файл — см. отдельный раздел ниже |

Смотреть: `journalctl -u x-ui -n 60`, `/usr/local/x-ui/bin/config.json`, `error.log` из секции `log` конфига.

## L3 — порт не доступен снаружи

| Изнутри `ss -tlnp` | Снаружи TCP | Вывод |
|---|---|---|
| слушает | refused | между нами NAT/прокси отдаёт отказ |
| слушает | таймаут | режет фаервол хоста или security group провайдера |
| слушает на 127.0.0.1 | недоступно | в панели заполнено поле `listen` — его надо очистить |
| не слушает | недоступно | следствие L2, чинить там |

## L4 — TLS / Reality

| Признак | Причина |
|---|---|
| TLS-хендшейк рвётся | не тот SNI, на порту другой протокол, активная фильтрация |
| Reality: сервер не достукивается до `dest` | ломается запасной путь: посторонний хендшейк некуда проксировать. Проверку делает `openssl s_client` на сервере; если её не удалось выполнить, отчёт скажет «судить нельзя», а не «недоступен» |
| `dest` без TLS 1.3 | требование Reality не выполнено, нужен другой dest |
| `publicKey` не выводится из `privateKey` | ключи разъехались, ссылку надо перевыпустить (`xray x25519 -i <priv>`) |
| пустой `serverNames` / `shortIds` | конфиг неполный |
| TLS без сертификата | инбаунд с `security: tls`, но `certificates` пуст |

Нормально и ожидаемо: снаружи виден сертификат чужого сайта — так маскировка Reality и выглядит.

## L5 — конфиг внутренне противоречив

- `flow: xtls-rprx-vision` возможен только при `vless` + `tcp` + `reality|tls`. С `ws`/`grpc` — не работает.
- `vless` требует `encryption=none` в ссылке.
- Reality работает **только** с RAW (он же TCP), XHTTP и gRPC. С `ws`, `httpupgrade`, `kcp` конфиг не соберётся, и Xray отвергнет его целиком.
- Путь у `ws`/`httpupgrade` должен начинаться со слеша и совпадать на клиенте и сервере.
- Заполненное поле `listen` делает инбаунд локальным.

## L6 — сервер сам не ходит в интернет

DNS не резолвит (`/etc/resolv.conf`, DNS-секция конфига Xray); HTTPS наружу не идёт (блокировки провайдера); правила `routing` с `outboundTag: blocked` режут нужные домены; часы сервера разошлись больше чем на пару минут — для VMess это ломает аутентификацию.

## L7 — на сервере всё в порядке, а туннель не работает

Если L0–L6 чистые, а `test` даёт FAIL — фильтрация между клиентом и сервером: DPI провайдера, блокировка по IP, MTU. Проверить тот же конфиг из другой сети (мобильный интернет).

Если оттуда работает — поднимать запасной канал с другим транспортом (`clone-inbound` с другой схемой).

Перед выводом убедись, что понимаешь свою точку обзора: если рабочая машина сама сидит за одним из этих VPN, её внешний адрес совпадёт с адресом сервера и сверка IP ничего не докажет, а недоступность соседнего сервера будет говорить о маршруте через VPN, а не о самом сервере.

## Устаревшая копия клиента внутри инбаунда

Самый неочевидный отказ: всё зелёное — панель отвечает, инбаунд включён, клиент
активен, порт открыт, TLS-хендшейк проходит, — а туннель не работает.

Причина в устройстве панели 3.x: клиент там самостоятельная сущность
(`/panel/api/clients/*`), которая прикрепляется к инбаундам, а внутри инбаунда
хранится лишь его копия. Копия может устареть. Тогда:

* `/panel/api/clients/subLinks/{subId}` отдаёт верную ссылку;
* `/panel/api/clients/links/{email}` — тоже по копии, тоже мёртвую;
* `/panel/api/inbounds/allLinks` и `inbounds/list` — мёртвый идентификатор;
* Xray работает по значению из таблицы клиентов, то есть по верному.

Признак в тесте: `SSLEOFError / UNEXPECTED_EOF_WHILE_READING` либо молчаливый
таймаут при живом TCP. Для Reality это закономерно: сервер не узнаёт клиента,
считает его посторонним и уводит хендшейк на сайт-маскировку.

**Правило: идентификатор клиента брать только из таблицы клиентов.** В коде это
`api/registry.authoritative_client()`, им пользуется `resolve_client`, поэтому
`link`, `test` и `diag` уже защищены. Читать `uuid` прямо из инбаунда нельзя.

Поиск — `reality-check drift`, починка копий — `reality-check fix-drift
<сервер> --apply` (пересохраняет клиента его же данными, панель рассылает
запись по инбаундам; действующие ссылки при этом не ломаются).

## Инбаунд на узле, а проверяли хост панели

Если у инбаунда задан `nodeId`, он поднят не на хосте панели, а на узле, и
подключаться надо к адресу узла (`/panel/api/nodes/list`). Проверка по адресу
панели даст ложное «порт закрыт». `inventory` показывает узел и адрес для
каждого инбаунда, `diag` подставляет адрес узла автоматически.

## Один сломанный инбаунд роняет весь сервер

Xray загружает конфиг целиком: если хоть один инбаунд некорректен, процесс не
стартует вовсе и не работает **ни один** инбаунд, включая заведомо исправные.
Снаружи выглядит как «умер весь сервер», хотя виноват один инбаунд.

Живой пример: инбаунд `vless/httpupgrade/reality`. Reality допустим только с
RAW (он же TCP), XHTTP и gRPC, поэтому Xray отвергал файл:

    failed to build inbound config with tag in-41917-tcp >
    REALITY only supports RAW, XHTTP and gRPC for now

Как опознать: процесса `xray` в `ps` нет, портов инбаундов в `ss -tlnp` нет,
панель жива (она отдельный процесс). Точная причина — в `probe`: панель
показывает `xray: error` вместе с текстом ошибки, SSH для этого не нужен.

Лечение — убрать виновника, не трогая остальных:

    reality-check inbound-enable <сервер> <id> --off --apply

Выключенный инбаунд не попадает в конфиг, панель пересобирает файл и
перезапускает Xray. После рестарта дай процессу подняться: тест, запущенный
через несколько секунд после старта, может ложно провалиться.

## Проверка, которая не выполнилась, — не признак поломки

Отдельно стоит помнить при чтении отчётов: команда, отклонённая фильтром
читающих команд, даёт пустой вывод, и его легко принять за отрицательный
результат. В `check_dest` это приводило к ложному «сервер не достукивается до
dest». Теперь такие случаи возвращают `ok=None` и явно говорят, что судить
нельзя. Тот же принцип стоит держать и при ручных проверках.
