# Разобранные случаи

Оба разбора настоящие: сделаны этим инструментом на боевых серверах, с проверкой
результата сквозным тестом. Здесь они как образец рассуждения — по такому же
пути идёт диагностика любой новой поломки.

---

## Случай 1. «Конфиги не работают», хотя сервер полностью исправен

**Жалоба.** У части людей выданные из панели конфиги не работают. При этом
панель отвечает, инбаунды включены, клиенты активны, трафик у других идёт.

**Что показывали проверки.** Слои L0–L3 зелёные: панель пускает, инбаунд и
клиент в порядке, порт принимает соединения, TLS-хендшейк проходит. И тем не
менее сквозной тест падал с `SSLEOFError: UNEXPECTED_EOF_WHILE_READING`.

Такая комбинация обманчива именно потому, что выглядит как сетевая проблема.
Для Reality она закономерна: сервер не узнаёт клиента, считает его посторонним
и уводит его хендшейк на сайт-маскировку. Отказа клиент не получает — получает
чужой TLS, то есть тишину.

**Решающий эксперимент.** Один и тот же инбаунд, один и тот же клиент,
отличается только идентификатор:

| источник идентификатора | результат |
|---|---|
| копия клиента внутри инбаунда | FAIL |
| таблица клиентов панели | **PASS**, выходной IP совпал с сервером |

**Причина.** В панели 3.x клиент — самостоятельная сущность
(`/panel/api/clients/*`), которая прикрепляется к инбаундам, а внутри инбаунда
хранится лишь его копия. Копии устарели. В результате панель имеет два
генератора ссылок, которые расходятся:

* `clients/subLinks/{subId}` — отдаёт верную ссылку;
* `clients/links/{email}` — вопреки префиксу `clients/`, строится по копии и отдаёт мёртвую;
* `inbounds/allLinks` и `inbounds/list` — отдают мёртвый идентификатор.

Xray при этом работает по значению из таблицы клиентов, то есть по верному.
Ломались ровно те люди, чьи ссылки брали из инбаунда.

**Вывод, закреплённый в коде.** Идентификатор клиента берётся только из таблицы
клиентов — `api/registry.authoritative_client()`. Читать `uuid` прямо из
инбаунда нельзя, это и есть ловушка. Поиск таких расхождений — `drift`,
починка копий — `fix-drift`.

**Побочная находка.** Инбаунды, отсутствовавшие в применённом конфиге, сперва
выглядели как «не поднялись». На деле они были подняты на другом узле
мультинодовой панели, и проверять их следовало по адресу узла. Поэтому
`inventory` показывает узел и адрес подключения, а проверки идут по адресу
узла, а не панели.

## Случай 2. «Не работает вообще ничего»

**Жалоба.** Сервер не работает целиком.

**Что показали проверки.** Процесса `xray` в `ps` нет, портов инбаундов в
`ss -tlnp` нет, но панель жива — она отдельный процесс. `probe` сразу назвал
причину, взяв её из API панели:

    Xray: error — failed to load config files: [bin/config.json] >
    failed to build inbound config with tag in-41917-tcp >
    REALITY only supports RAW, XHTTP and gRPC for now

**Причина.** Один инбаунд был создан как `vless/httpupgrade/reality`. Reality
допустим только с RAW (он же TCP), XHTTP и gRPC. Xray загружает конфиг целиком
и отвергает файл полностью — вместе с исправными инбаундами. Инбаунд на 443,
до этого набравший 4.8 ГБ трафика, умер в тот момент, когда рядом появился
некорректный сосед с нулевым трафиком.

**Починка.** Выключить виновника, не трогая остальных:

    reality-check inbound-enable de-2 2 --off --apply

Выключенный инбаунд не попадает в конфиг: панель пересобрала файл, Xray
запустился, оба оставшихся инбаунда проверены сквозным тестом и отдали
выходной IP сервера.

**Чему научил случай.** Формулировка «умер весь сервер» почти никогда не
означает, что сломано всё. Стоит искать один неверный элемент, из-за которого
не грузится общий конфиг.

## Две ошибки в самих проверках, найденные по ходу

Полезно помнить при чтении любых отчётов.

**Проверка, которая не выполнилась, — не признак поломки.** Команда проверки
доступности сайта-маскировки содержала перенаправления, а фильтр читающих
команд их запрещает. Проверка молча не выполнялась, а пустой вывод трактовался
как отрицательный результат — и отчёт уверенно сообщал «сервер не достукивается
до dest», хотя сервер достукивался. Теперь невыполненная проверка возвращает
`ok=None` и прямо говорит, что судить нельзя.

**Гипотезу нельзя проверять на сломанном образце.** Версия про uTLS-фингерпринт
сперва проверялась на инбаунде, который был неисправен по другой причине. Там
падали все фингерпринты — и версия выглядела опровергнутой. Проверять её надо
было на заведомо исправном инбаунде.

**Точка обзора — часть измерения.** Машина, с которой шли проверки, сама
работала через один из этих же VPN, поэтому её внешний адрес совпадал с
адресом сервера. Из-за этого сверка выходного IP для того сервера ничего не
доказывала, а недоступность соседнего узла характеризовала маршрут через VPN,
а не сам узел. Перед выводами стоит знать свой реальный внешний адрес.
