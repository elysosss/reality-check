# Правила работы в этом репозитории

## Секреты
- `config/servers.yaml` содержит токены и пароли от панелей. Он в `.gitignore` — **никогда** не коммитить, не печатать целиком, не вставлять в отчёты.
- При выводе секретов пользоваться `util.mask()`, при записи структур в `runs/` — `util.scrub()`.
- Приватные ключи Reality не логировать. Публичный ключ — можно, он и так в ссылке.

## Изменения на серверах
- Любая мутирующая команда (`add-client`, `del-client`, `clone-inbound`) по умолчанию работает в dry-run. Реальная отправка — только с явным `--apply`.
- Перед `update`/`del` сохранять снапшот текущего инбаунда в `runs/snapshots/`.
- Диагностика (`diag`, `probe`) не меняет состояние: по SSH выполняются только читающие команды, список — в `diag/ssh.py`. Мутации по SSH — только по прямой просьбе пользователя, с `allow_write=True`.
- Панель не трогать массово: никаких `resetAllTraffics`, `bulkDel`, `delDepletedClients` без отдельного явного запроса.

## Работа с API 3x-ui
- Не хардкодить набор эндпоинтов: версии панелей разные. Сначала `probe`, затем опираться на `runs/caps/<server>.json` (`api.probe.has()`).
- Поля `settings`, `streamSettings`, `sniffing`, `allocate` — **JSON-строки внутри JSON**. На чтение распаковывать, на запись запаковывать через `models.Inbound.to_payload()`. Если отправить объектом, панель ответит `success:true`, а Xray потом не поднимется.
- Ответ всегда конверт `{success, msg, obj}`; при ошибке HTTP-код часто 200. Проверять `success`, а не статус.
- Новые конфиги делать клонированием заведомо рабочего инбаунда (`clone_payload`), а не сборкой схемы с нуля.

## Проверка результата
- «Панель ответила 200» не является доказательством. Единственная честная проверка — `reality-check test`: локальный xray, запрос через SOCKS5, сверка внешнего IP.
- `test` доказывает лишь, что туннель **поднимается**. Стабильность «после подключения» (потери запросов, обрыв закачки, провал под параллелью) видит только `reality-check stress` — одиночный запрос деградацию не ловит.
- Если тест провалился — не гадать, а запускать `reality-check diag` и читать первый провалившийся слой.

## Стиль
- Комментарии и сообщения — по-русски, как и весь остальной код здесь.
- Комментировать «почему», а не «что»: очевидное из кода не дублировать.

## Идентификатор клиента

- В ветке 3.x клиент — самостоятельная сущность, а внутри инбаунда лежит его **копия**, которая может устареть. Идентификатор брать только через `api/registry.authoritative_client()`; читать `uuid` прямо из инбаунда — ошибка, из-за неё панель раздаёт мёртвые ссылки.
- Врут **не только** `inbounds/*`: по копиям из инбаунда строится и `clients/links/{email}`, проверено. Доверять можно ровно двум эндпоинтам: `clients/get/{email}` для идентификатора и `clients/subLinks/{subId}` для ссылок. Префикс `clients/` сам по себе гарантией не является.

## Выводы о причинах

- Один некорректный инбаунд роняет **весь** конфиг Xray: процесс не стартует, и не работает ни один инбаунд. При «умер весь сервер» искать один неверный элемент, а не общую поломку.
- Инбаунд с `nodeId` поднят на узле: проверять его по адресу узла, иначе диагноз ложный.
- Проверка, которая не выполнилась, — не признак поломки. Если команда отклонена фильтром или бинаря нет, возвращать `ok=None`, а не `False`.
- Гипотезу проверять на заведомо исправном образце: на сломанном по другой причине проваливаются все варианты, и версия выглядит опровергнутой.
- Помнить свою точку обзора: если рабочая машина сама сидит за одним из этих VPN, сверка внешнего IP для этого сервера ничего не доказывает.
- «Панель зелёная, TCP есть, а TLS-хендшейк висит по таймауту» — фильтрация на пути, не поломка сервера. Отделять хендшейком на самом сервере (`openssl s_client` на `127.0.0.1:<порт>`): если локально проходит — виновата сеть клиент→сервер.
- В RU DPI режет Reality по двум осям. SNI-маскировка: `vk.com` заблокирован, живёт `vk.ru` — менять `serverNames` и `target`. Клиентский uTLS-fingerprint: `chrome`/`safari`/`ios` глушатся, `firefox`/`edge`/`random` проходят — менять `realitySettings.settings.fingerprint`. Смена `serverNames`/`fingerprint` делает старые ссылки недействительными.
- Инбаунд за обратным прокси (nginx терминирует TLS) описывает **внутреннее** плечо: в панели у него `security: none`, локальный `listen` и внутренний порт. Клиент же идёт на 443 по TLS с доменом. Поэтому `test`/`stress`, собирающие конфиг из инбаунда, дают по такому инбаунду **ложный FAIL** — проверять надо параметрами из клиентской ссылки. Пока в инструменте нет переопределения клиентского плеча, это делается вручную.
- Для xhttp за nginx нужен `proxy_pass` с `proxy_http_version 1.1` и выключенной буферизацией (`proxy_buffering off`, `proxy_request_buffering off`). `grpc_pass` годится только для транспорта gRPC: простые запросы сквозь него проходят, а потоковая сессия рвётся с `read/write on closed pipe` — симптом выглядит как сетевой сбой, а не как ошибка конфигурации.
